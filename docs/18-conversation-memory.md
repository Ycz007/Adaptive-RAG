# 会话上下文管理

普通聊天和 SSE 流式聊天使用同一套数据库历史、上下文构建和摘要保存逻辑。客户端继续传入上一轮返回的 `session_id` 即可续接对话。

## 请求流程

1. `ChatService._initial_state()` 校验会话归属，读取 `sessions.summary`、`summary_until_message_id` 和游标之后的全部消息。
2. 护栏通过后，`prepare_memory` 限制历史大小；有工具调用时，规划器也收到摘要和原始角色的历史消息。
3. 检索或工具执行结束后，`compact_memory` 使用 `ContextBuilder` 重新组装回答输入，将系统提示、当前问题、历史、摘要、证据和工具输出一起计入预算，预留 700 tokens 回答及安全余量。
4. `generate_answer` 使用已构建的消息调用模型，随后执行忠实度检查。检查和自纠错也收到相同的摘要和历史，避免把用户此前提供的信息误判为无依据。
5. 最终的用户消息、助手消息、摘要和覆盖游标在同一事务中提交。数据库原始消息不会因压缩被删除。

## 增量摘要

默认最多保留最近 8 个完整对话轮次，历史与摘要另有 12,000 tokens 上限。达到轮数或预算上限后，将即将移出窗口的旧消息和已有摘要合并，再保留最近的完整轮次。大批旧历史分段总结，每一段都携带上一段摘要，避免只总结最后若干条。

`summary_until_message_id` 表示摘要已经覆盖的最后一条消息。下一轮只加载该 ID 之后的原文，避免重复或遗漏。摘要错误或模型失败时不提交新的摘要和游标，本次请求会报错，可以重试；原始历史仍在数据库中。

摘要使用明确标记的数据消息传入，历史 user / assistant 消息保留原角色，不提升为系统指令。历史状态仅供参考，订单现状仍应通过工具查询。

## 配置

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `TOKEN_BUDGET` | 128000 | 模型上下文总预算，应按实际模型设置 |
| `MEMORY_RECENT_TURNS` | 8 | 优先保留的最近完整轮次上限 |
| `MEMORY_HISTORY_TOKEN_LIMIT` | 12000 | 历史消息和摘要的预算上限 |
| `CONTEXT_SAFETY_TOKENS` | 512 | 预留的输入安全余量 |

预算沿用项目的字符估算方式并加上消息包装开销，不是模型 tokenizer 的精确计数。检索证据和工具输出分别最多使用剩余预算的约三分之一、六分之一。只裁剪模型输入，不修改原始检索和工具结果。当前问题和固定提示已经超预算时返回明确错误。

原 `COMPRESS_SOFT_RATIO`、`COMPRESS_HARD_RATIO`、`AUTO_COMPACT_RATIO` 仍供旧压缩辅助函数使用，在线聊天已改为上述预算构建流程。

## 数据库兼容

- 新库由 ORM 创建 `sessions.summary_until_message_id`，初始值为 0。
- 已有本地 SQLite 文件在应用启动时自动补列，保留会话和消息。
- PostgreSQL 部署需要先对目标库应用 Alembic `0003_session_summary_cursor` 迁移，再启动新代码。
- 旧摘要没有覆盖游标，不能推断覆盖范围；新代码从完整原始历史重新构建摘要，不直接复用这类摘要。

## 验证与边界

`tests/unit/test_context_builder.py` 覆盖输入预算、完整轮次、增量摘要、工具结果裁剪和摘要失败；`tests/integration/test_conversation_memory.py` 覆盖多轮历史进入回答与规划、重开数据库后的摘要恢复、SSE 续接、会话隔离和旧 SQLite 升级。

会话归属检查使用当前 API 提交的 `user_id`，与现有订单接口的身份方式一致；它不替代登录认证。Redis 仍用于原有检索缓存和限流，本阶段没有新增会话缓存，也未加入同一会话并发请求的协调。
