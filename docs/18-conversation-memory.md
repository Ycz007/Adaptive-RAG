# 会话上下文管理

普通聊天和 SSE 流式聊天使用同一套数据库历史、上下文构建和摘要保存逻辑。客户端继续传入上一轮返回的 `session_id` 即可续接对话。

## 请求流程

1. `ChatService._initial_state()` 先在数据库校验会话归属和消息版本，再查询 Redis 快照；未命中、损坏或 Redis 故障时读取数据库原文。
2. 护栏通过后，`prepare_memory` 按预算利用率执行三级压缩；有工具调用时，规划器也收到摘要和原始角色的可见历史消息。
3. 检索或工具执行结束后，`compact_memory` 使用 `ContextBuilder` 重新组装回答输入，将系统提示、当前问题、历史、摘要、证据和工具输出一起计入预算，预留 700 tokens 回答及安全余量。
4. `recover_tool_results` 允许 Agent 在本轮对被截断结果按需加载原文页，加载后重新计算预算。`generate_answer` 使用已构建的消息调用模型，随后执行忠实度检查。检查和自纠错收到相同的可见历史、摘要及已压缩的证据/工具输出，并分别执行输入预算检查，避免后续节点重新塞入原始大输出。
5. 最终的用户消息、助手消息、摘要和覆盖游标在同一事务中提交。提交成功后，从数据库读取已提交快照并写入 Redis；数据库原始消息不会因压缩被删除。

## 128k 预算与三级压缩

利用率以**本次压缩前**的系统提示、摘要、全部未摘要历史、当前问题、检索证据、工具输出、预留回答空间和安全余量之和除以 `TOKEN_BUDGET` 计算。更高级别累计执行前面的措施，避免工具截断后把原本已达到 85% 的输入误判为低等级。

| 利用率 | 动作 |
| --- | --- |
| < 50% | 保留历史和工具输出；不会仅因超过 8 轮而摘要 |
| ≥ 50%、< 70% | 截断过长工具输出，预览最多 400 字符 |
| ≥ 70%、< 85% | 工具预览收紧到 160 字符；模型输入收缩为最近 8 个完整轮次和已有摘要 |
| ≥ 85% | 在上述措施基础上，将移出窗口的完整旧消息与已有摘要合并，必要时进一步缩窗以降低输入规模 |

128,000 预算下，三个等级分别从估算用量 64,000 / 89,600 / 108,800 起触发。70% 阶段仅改变可见窗口，未摘要旧消息仍保留在 State 和数据库中，不推进摘要游标；之后达到 85% 时仍能参与总结。大批旧历史分段总结，每一段都携带上一段摘要，避免只总结最后若干条。

`summary_until_message_id` 表示摘要已经覆盖的最后一条消息。下一轮只加载该 ID 之后的原文，避免重复或遗漏。摘要错误或模型失败时不提交新的摘要和游标，本次请求会报错，可以重试；原始历史仍在数据库中。

摘要使用明确标记的数据消息传入，历史 user / assistant 消息保留原角色，不提升为系统指令。历史状态仅供参考，订单现状仍应通过工具查询。

## 配置

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `TOKEN_BUDGET` | 128000 | 模型上下文总预算，应按实际模型设置 |
| `MEMORY_RECENT_TURNS` | 8 | 70% 起采用的最近完整轮次上限 |
| `CONTEXT_SAFETY_TOKENS` | 512 | 预留的输入安全余量 |
| `COMPRESS_SOFT_RATIO` | 0.50 | 工具结果截断阈值 |
| `COMPRESS_HARD_RATIO` | 0.70 | 滑动窗口收缩阈值 |
| `AUTO_COMPACT_RATIO` | 0.85 | 历史摘要阈值 |
| `SESSION_CACHE_TTL_SECONDS` | 1800 | 会话快照存活时间（秒） |
| `SESSION_CACHE_MAX_BYTES` | 2000000 | 单个缓存快照的大小上限 |

预算沿用项目的字符估算方式并加上消息包装开销，不是模型 tokenizer 的精确计数。最终模型输入还执行硬预算检查；极端长的检索证据或工具元数据会额外裁剪。只裁剪模型输入，不修改原始检索和工具结果。当前问题和固定提示已经超预算时返回明确错误。

`COMPRESS_SOFT_RATIO`、`COMPRESS_HARD_RATIO`、`AUTO_COMPACT_RATIO` 已接入在线 `ContextBuilder`，必须满足 `0 < soft < hard < auto < 1`。旧的 `MEMORY_HISTORY_TOKEN_LIMIT` 已移除，不再提前触发摘要。

## Redis 会话缓存

配置 `REDIS_URL` 且启动连接成功时，自动启用 `RedisSessionContextCache`。缓存保存用户 ID、会话 ID、摘要、覆盖游标、尚未被摘要的完整消息及其数据库 ID，不保存检索结果或工具执行结果。

Key 为 `chat:context:v1:` 加身份和数据库版本元数据的 SHA-256。版本包含最新消息 ID、摘要覆盖游标和摘要内容。每次读取仍查数据库会话元数据及最新消息 ID；命中时跳过消息正文查询。这样延迟到达的旧写入只能写入旧版本 Key，不会覆盖新版本；过期 Key 由 Redis TTL 回收。

数据库提交成功后才写快照；提交失败不写缓存。读取或写入异常、无效 JSON、身份/版本不匹配、快照超限时直接降级。缓存失败不会把已成功提交的回答变成错误。未连接 Redis 时使用数据库，不启用进程内会话缓存。

## 数据库兼容

- 新库由 ORM 创建 `sessions.summary_until_message_id`，初始值为 0。
- 已有本地 SQLite 文件在应用启动时自动补列，保留会话和消息。
- PostgreSQL 部署需要先对目标库应用 Alembic `0003_session_summary_cursor` 迁移，再启动新代码。
- 旧摘要没有覆盖游标，不能推断覆盖范围；新代码从完整原始历史重新构建摘要，不直接复用这类摘要。

## 工具结果持久化与按需恢复

业务工具返回结果后，如果 `output` 的字符串长度超过 160 字符，执行节点先保存完整 `ToolResult` JSON，再交给压缩节点生成预览。阈值按三级压缩最严格的 160 字符设置，确保未来可能被截断的结果有恢复来源。加载工具返回的页面不会再次归档，也不会被 160/400 字符预览规则再次截断；最终总预算检查仍然有效。

完整原文保存在当前 `DATABASE_URL` 对应数据库的 **`tool_outputs` 表、`output_json` 字段**。默认 SQLite 文件是 `data/local/app.db`；配置 PostgreSQL 时记录在 PostgreSQL 中，没有另外生成磁盘 JSON 文件或使用 Redis 作为持久化存储。

每条记录包含 `result_ref`（`tout_` 加 UUID）、所属用户、会话、请求 trace、工具名、完整 JSON、预览、字符总数和创建时间。结果随本轮聊天事务提交；本轮失败则回滚。已有结果为历史快照，加载不会重新执行业务操作，也不能证明当前业务状态。

截断预览中提供 `result_ref`、`total_chars` 和 `load_tool: load_tool_result`。Agent 可以调用：

```json
{
  "result_ref": "tout_0123456789abcdef0123456789abcdef",
  "offset": 0,
  "limit": 1000
}
```

`offset` / `limit` 按 JSON 原文字符计算，`limit` 默认 1000、最大 4000。返回 `content`、`offset`、`next_offset`、`has_more`、`total_chars` 等信息。按 `next_offset` 加载并拼接全部页面后，可以解析出原始完整工具消息。引用不存在、用户不符或会话不符时均返回相同的未找到结果，不接受任意文件路径。

同轮恢复：新增 `recover_tool_results` 节点，只在结果被截断且有引用时询问模型是否需要加载。仅允许加载本轮已知引用、去重重复页面，并与原业务工具共享 `MAX_TOOL_CALLS` / `MAX_AGENT_STEPS` 限额；预览足够时不加载，不重新执行业务工具。

跨轮恢复：每轮初始化读取本会话最近 10 条结果的轻量目录，供规划器选择 `load_tool_result`；只读取元数据和预览，不自动把大原文放回上下文。明确给出 `tout_...` 的恢复请求会进入工具路径，引用仍需经过数据库权限检查。重启后仍可加载已经提交的记录。

新建表由应用启动时的 ORM 建表流程创建；使用 Alembic 管理的部署需应用 `0004_tool_outputs` 迁移。当前不自动清理这些记录，保留周期需要按部署的数据保留策略另行设置。

## 验证与边界

`tests/unit/test_compression_thresholds.py` 验证三个阈值的前一 token、等于阈值、后一 token 和 70% 到 85% 的历史完整性；`test_context_builder.py` 验证预算与摘要失败；`test_session_cache.py` 验证缓存过期、损坏和版本隔离。`tests/integration/test_conversation_memory.py` 覆盖真实图节点的三级触发、普通/SSE 会话缓存读写、消息正文查询跳过、数据库版本变化、回滚、Redis 故障、会话隔离和数据库升级。

会话归属检查使用当前 API 提交的 `user_id`，与现有订单接口的身份方式一致；它不替代登录认证。版本 Key 解决缓存陈旧写入问题，同一会话并发生成及摘要更新的数据库协调仍需另行处理。
